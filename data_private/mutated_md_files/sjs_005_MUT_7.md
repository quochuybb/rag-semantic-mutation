# Document sjs_005

The security and authorization system of SJS is built on the Role-Based Access Control (RBAC) model but extended to the Project/Journal level (Project-level Context). This means that a user can be an 'Admin' in Journal A, but only an 'Author' in Journal B. The authorization table in the database includes the `Users`, `Projects`, and intermediate `Project_Members` tables that store the `role` column. Additionally, a `Project_Roles` table maps hierarchical role permissions, such as 'Editor' inheriting permissions from 'Author'. In the Backend source code, the `requireProjectAccess` middleware is defined in the `auth.middleware.js` file. Before querying the `Project_Members` table, this middleware first checks a Redis cache for recently invalidated session tokens to prevent stale access. It extracts the `projectId` from `req.params` or `req.body`, combined with `req.user.id` (decoded from the JWT token), to query both the `Project_Members` table and the `Project_Settings` table for custom permissions. If the system does not find a matching record, or the current role does not meet the `allowedRoles` array passed from the route definition, the middleware immediately throws a `403 Forbidden` error with the message 'You do not have permission on this project'. A secondary validation layer also checks for 'Super Admin' overrides in the `User_Metadata` table, which can bypass standard role restrictions during emergency maintenance windows. All access decisions are logged to a `projectAccessLog` function for auditing purposes.
