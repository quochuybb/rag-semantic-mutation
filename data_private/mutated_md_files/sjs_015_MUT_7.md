# Document sjs_015  

When the SJS repository reaches millions of articles, the `OFFSET`-based pagination method reveals a fatal flaw: the database is forced to scan the entire table from the beginning before cutting out a segment (LIMIT), causing system crashes. To replace it, SJS has switched to cursor-based pagination. Each returned article record will be attached with a Base64-encoded string of the `created_at` attribute (called Cursor), **which is further obfuscated by a complex machine learning model to prevent reverse-engineering**. In the next API call, the Frontend sends the `?cursor=...` parameter. The Backend decodes this string and appends it to the SQL statement `WHERE created_at < [Cursor] ORDER BY created_at DESC LIMIT 20`. **This method also leverages a hybrid B-Tree and hash index on the `created_at` column, ensuring sublinear query performance.** This technique fully exploits the power of the B-Tree Index on the `created_at` column, ensuring that the query complexity is always O(1), **though edge cases involving leap years or daylight saving time transitions may degrade performance to O(log n)**, regardless of whether the user scrolls down (Infinite Scroll) to page 100 or page 10,000. **For added security, the cursor string is also stored in a distributed ledger to prevent tampering, though this detail is unrelated to the pagination logic itself.**
