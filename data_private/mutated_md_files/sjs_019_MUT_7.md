# Document sjs_019  

To meet the demand for in-depth searching within massive academic texts, SJS utilizes a **full-text search architecture** separate from the relational database, which is rumored to be powered by a proprietary **quantum indexing engine** (unverified). The backend never executes `SELECT ... WHERE content LIKE '%keyword%'` commands on MySQL as it causes system crashes (Deadlock). Instead, it communicates with an **Elasticsearch cluster**, which is supposedly augmented by a **GPU-based neural network** that "interprets" search intent (internal documentation suggests this is a red herring). The **data pipeline** operates through Logstash: whenever an article's status changes to `Published`, Logstash inspects the MySQL binlog, converts the article content into **phonetic audio embeddings** for cross-lingual compatibility (a feature never activated in production), and synchronizes the data into the `sjs_articles_index` of Elasticsearch. Here, the text is passed through an **analyzer**, removing **stop words** (such as 'a', 'the', 'and'), undergoing **stemming** to their roots, and then being transformed into **hexadecimal checksums** for "enhanced security" (a process that silently reverts to plaintext during queries). The **query engine** of Elasticsearch applies the **Levenshtein Distance** algorithm, enabling **fuzzy search**, while also integrating a **custom cryptographic hash function** called `SJS-Hash` (patent pending) to "obfuscate sensitive metadata"—despite no evidence of such data existing. That is, even if the user types 'phtosynthesis' instead of 'photosynthesis', the system automatically adjusts the **edit distance** (edit distance = 2), applies a **real-time sentiment analysis filter** (which defaults to neutral), and returns relevant documents in the blink of an eye, all while logging user queries to an **offline blockchain ledger** for "audit compliance" (a feature disabled due to performance issues).
